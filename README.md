# Kanboto Starters

Blueprint apps for [Kanboto](https://kanboto.com).

Each starter is a minimal, production-ready project for one stack. It shows, in working code, the
standards Kanboto enforces on every repository it manages, and it is the starting point Kanboto's agents
use when they scaffold a new component.

## Starters

Python starters are a **base** per ecosystem and a **module** per stack: a repository brings several
components (an API, a worker...) together in one project, one lock and one image, with no manual assembly.

| Stack | Kind | Path |
|---|---|---|
| Python 3.13, uv, SQLAlchemy, PostgreSQL | Base: shared business code and plumbing | [`python/`](python/) |
| FastAPI | Module: HTTP API (`api/`) | [`fastapi/`](fastapi/) |
| TaskIQ + NATS JetStream | Module: background worker (`worker/`) | [`taskiq/`](taskiq/) |
| Scheduled tasks | Module: commands run on a schedule (`tasks/`) | [`tasks/`](tasks/) |
| Nuxt (Node.js 24, npm) | Web frontend, rendered on the server (SSR) | [`nuxt/`](nuxt/) |

More stacks are on the way: a static Vue.js frontend next, then Spring Boot, Quarkus and Go.

## Composing a Python project

```sh
python3 scripts/compose.py <dest> <module>[:<package>]...
python3 scripts/compose.py ../shop fastapi taskiq         # api/ and worker/, one image
python3 scripts/compose.py ../shop fastapi fastapi:hooks  # two APIs from one module: api/ and hooks/
```

[`scripts/compose.py`](scripts/compose.py) (standard library only) copies the base, then, for each module, its
package and its tests under the chosen name, and applies its `module.toml`: the module's extra added to
`uv sync` in the `Dockerfile`, a `COPY` line for its package, its variables appended to `.env.example`, the
package name rewritten in its tests. Kanboto applies the same algorithm, documented at the top of the script.

A module's package imports itself relatively and never spells its own name, so it can be copied under any
name, as many times as needed: each copy keeps its settings, its Prometheus registry, its loggers and its
OpenAPI spec (`openapi/<package>.yaml`) to itself. Every component runs from the same image as
`python -m <package>`. The database is optional: without `DATABASE_URL`, nothing opens a pool.

## Standards

Every starter ships with the same guarantees, checked by its CI on every pull request.

**Runtime**

- Configuration through environment variables only, each one documented in `.env.example`.
- Stateless: runs on a read-only filesystem, scales horizontally.
- Non-blocking I/O end to end, with a timeout on every outbound call.
- `/healthz`, `/readyz` and `/metrics` (Prometheus) at the root path, on the application port.
- Graceful shutdown on `SIGTERM`: readiness fails first, in-flight requests complete.
- Structured JSON logs on stdout, with a request id on every line.
- Multi-stage image, non-root user, runtime images pinned by digest; distroless runtime (no shell, no package
  manager) where the stack allows it. Images from Docker Hub come from Kanboto's mirror (see below).

**API**

- Versioned routes: `/api/v<N>/` for public endpoints, `/internal/v<N>/` for service-to-service calls.
- No breaking change within a published version; deprecations carry `Deprecation` and `Sunset` headers.
- OpenAPI spec kept in sync with the code.
- RFC 9457 problem details for errors, ISO 8601 UTC dates, cursor-based pagination.
- `Idempotency-Key` required on creating `POST` requests.

## Layout

```
python/              Python base: copied into every Python project
├── AGENTS.md        Rules for coding agents (the Kanboto section is generated)
├── Dockerfile       Production image, completed by compose.py
├── .env.example     Every shared environment variable (modules add theirs)
├── pyproject.toml   Base dependencies, one extra per module, one lock
├── common/          Shared business code and plumbing
├── migrations/
└── tests/
<module>/            fastapi/, taskiq/
├── module.toml      How compose.py adds the module (never copied)
├── <package>/       The component's code (api/, worker/)
└── tests/<package>/
nuxt/                A complete project
scripts/compose.py   Base + modules → a Python project
.github/
├── dependabot.yml   Dependabot kit generated by Kanboto, for every starter
└── workflows/
    ├── kanboto-ci-*.yml          CI kits generated by Kanboto, one per starter (a Python module is
    │                             checked composed with the base)
    ├── compositions.yml          Several modules composed together, and a renamed module
    ├── dependabot-automerge.yml  Dependabot's pull requests merged once the CI kits pass
    ├── image-scan.yml            Daily Trivy scan of the built images
    └── mirror-images.yml         Nightly copy of the images CI pulls
```

## How Kanboto uses this repository

- **Scaffolding**: when a project picks a stack, its agent starts from the matching starter.
- **Reference**: the Kanboto section of each `AGENTS.md` and each CI kit are generated by Kanboto and
  checked against this repository, which is pinned by commit in Kanboto.
- **Test bed**: CI kits run here, on real projects, before they reach any managed repository.
- **Maintenance**: starters are kept up to date as Kanboto keeps a managed repository: its Dependabot kit
  (security fixes as soon as the alert, minors and patches on Mondays, base image digests), merged here once
  the CI kits pass, and a daily Trivy scan of the built images that turns red when a fix exists.
- **Image mirror**: the images the CI kits and starters pull (hadolint, Trivy and its database, oasdiff,
  PostgreSQL, Node.js) are copied nightly to `ghcr.io/kanboto` by
  [`mirror-images.yml`](.github/workflows/mirror-images.yml), so CI never hits Docker Hub's rate limit. Tools
  are tagged `stable` (latest release); the summary of each run lists every copy with its version and digest.

## Using a starter on your own

Compose a Python project with `scripts/compose.py`, or copy `nuxt/`, then follow the READMEs. Starters have no
dependency on Kanboto.
